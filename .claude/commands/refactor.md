# 리팩터링 커맨드

## 사용법

```
/refactor                   # 전체 스캔. 후보 보고만 하고 수정하지 않는다
/refactor <도메인>           # 예: /refactor tracking
/refactor <클래스명>         # 예: /refactor TrackingService
```

리팩터링은 **동작을 바꾸지 않는 구조 개선**이다. 동작 변경이 섞이면 멈추고 별도 이슈로 분리할 것을 제안한다.

## 동작 순서

### 1. 분석
- `$ARGUMENTS`로 대상을 정한다. 비어 있으면 `src/main/java/com/semosan/api` 전체를 스캔하고 **3단계 이전에 종료**한다 (보고만 함).
- 대상 코드와 해당 `.claude/rules/` 규칙을 읽는다. `rules/domain/<도메인>.md`가 있으면 반드시 먼저 읽는다.
- 아래 후보 유형을 찾는다. 추측하지 말고 실제 호출처를 grep으로 확인한 뒤 보고한다.

| 유형 | 예시 |
|---|---|
| 중복 로직 | 여러 서비스에 복제된 검증, 조회+예외, DTO 조립 코드 |
| 계층 위반 | 컨트롤러가 repository 직접 사용, 서비스가 다른 도메인 repository를 과도하게 직접 사용 |
| 프록시 무효화 | 같은 클래스 안에서 호출되는 `@Transactional`/`@Async` |
| 컨벤션 위반 | `ApiResponse` 미사용, Swagger 어노테이션이 컨트롤러에 있음, `ErrorStatus` 미사용, 서비스 트랜잭션 표준(클래스 readOnly) 미적용, enum이 `enums/` 밖에 있음 |
| 복잡도 | 긴 메서드, 깊은 중첩, 불필요한 추상화(구현이 하나뿐인 인터페이스 등) |
| 죽은 코드 | 호출처 없는 public 메서드, 쓰이지 않는 DTO, 필드, enum 값 |

### 2. 제안 (승인 대기)
후보를 표로 보여주고 **사용자 승인을 기다린다**. 승인 전에는 파일을 수정하지 않는다.

```markdown
| # | 위치 | 유형 | 문제 | 개선안 | 위험도 | 테스트 현황 |
|---|------|------|------|--------|--------|-------------|
| 1 | `XxxService.java:42` | 중복 로직 | ... | ... | 낮음 | 단위 테스트 있음 |
```

- 위험도: **낮음**(private 추출, 이름 변경) / **중간**(클래스 간 이동, 공통 컴포넌트 추출) / **높음**(트랜잭션 경계, 이벤트 흐름, 동시성 관련)
- 효과가 크고 위험도가 낮은 순으로 정렬한다.
- 사용자가 번호로 적용 대상을 고른다 (예: "1, 3번 진행").

### 3. 안전망 확인
- 적용 대상의 기존 테스트를 찾아 실행한다: `./gradlew test --tests <FQCN>`
- 테스트가 없거나 바꿀 동작을 검증하지 못하면 **현재 동작을 고정하는 테스트를 먼저 추가**하고 통과를 확인한다. 이 테스트는 리팩터링 전 코드 기준으로 작성한다.

### 4. 작업
- 한 번에 한 후보씩 적용하고, 단계마다 관련 테스트를 실행한다. 실패하면 다음 단계로 넘어가지 않는다.
- 테스트 코드의 기대값은 바꾸지 않는다. 바꿔야 한다면 동작 변경이므로 멈추고 보고한다.
- 모든 단계 후 `./gradlew test`를 실행한다. 인프라 부재로 인한 실패는 구분해서 보고한다.

### 5. 마무리
- 후보별로 무엇을 어떻게 바꿨는지 요약한다.
- 커밋 메시지를 추천한다. 동작 고정 테스트와 리팩터링은 커밋을 분리한다.

```
test: TrackingService 세션 종료 동작 고정 테스트 추가
refactor: TrackingService 세션 조회 검증 로직을 TrackingSessionService로 통합
```

## 금지 사항
- API 경로, 요청/응답 필드, `ErrorStatus`/`SuccessStatus` 코드 값 변경 금지 (클라이언트 호환성)
- DB 스키마, 마이그레이션 변경 금지
- `rules/domain/`에 명시된 구조 변경 금지 (예: tracking의 `TrackingPointFlushService` 분리 구조, notification의 AFTER_COMMIT 흐름)
- 요청받지 않은 범위의 포맷 변경이나 import 정리 금지
- 새 라이브러리 추가 금지
